# Build & Flash Architecture

Professional embedded development workflow for RX72N firmware.

## Overview

This project follows industry best practices for embedded development:

## Design Principles

### 1. Container-Based Build (Reproducibility)

**Why Docker?**
- Same build on Mac, Linux, Windows
- No "works on my machine" problems
- Versioned toolchain (GNURX GCC 8.3.0)
- Clean builds without polluting host

**What's in the container?**
```dockerfile
FROM msalau/rx-elf-gcc:latest
RUN apt-get install cmake make git
```

**Usage:**
```bash
./build.sh          # Builds Docker image once, then compiles
```

### 2. Host-Based Hardware Access (Practicality)

**Why not flash in Docker?**
- USB passthrough is unreliable across platforms
- Debuggers need direct hardware access
- Better error messages on host
- Simpler troubleshooting

**What runs on host?**
- `rfp-cli` (Renesas Flash Programmer)
- `rx-elf-gdb` (debugger client)
- `JLinkGDBServer` (debugger server)

**Usage:**
```bash
./flash.sh          # Runs rfp-cli on host Mac
./debug.sh          # Runs gdb on host Mac
```

### 3. Separation of Concerns

| Concern | Tool | Runs In | Why |
|---------|------|---------|-----|
| **Build** | CMake + Make | Docker | Reproducible cross-compilation |
| **Flash** | rfp-cli | Host | Needs USB E2 Lite access |
| **Debug** | GDB + J-Link | Host | Needs USB debugger access |

## Workflows

### Development Iteration

```bash
# 1. Edit code in your favorite editor
vim src/main.c

# 2. Build (fast incremental)
./build.sh                    # ~5-30 sec

# 3. Flash to hardware
./flash.sh                    # ~10 sec

# 4. Verify via UART
screen /dev/tty.usbserial-* 115200
```

### Debugging Session

```bash
# Terminal 1: Start GDB server (J-Link)
JLinkGDBServer -device R5F572NN -if JTAG -speed 4000 -port 2331

# Terminal 2: Build and debug
./build.sh
./debug.sh

# GDB is now connected:
(gdb) break main
(gdb) continue
(gdb) print led_thread
```

### Clean Build

```bash
rm -rf build
./build.sh                    # ~1-2 min (rebuilds ThreadX)
```

### CI/CD Pipeline

```yaml
# .github/workflows/build.yml
- name: Build Firmware
  run: ./build.sh

- name: Archive Artifacts
  uses: actions/upload-artifact@v3
  with:
    name: firmware
    path: |
      build/*.elf
      build/*.hex
      build/*.bin
```

**Note:** CI only builds - no flashing (no hardware in CI)

## Common Questions

### "Why not use `make flash`?"

**Answer:** Professional embedded teams separate build from hardware access.

**Before (bad):**
```bash
cd build
make flash              # ❌ Needs USB in Docker, platform-specific
```

**After (good):**
```bash
./flash.sh              # ✅ Host script, works everywhere
```

### "Why is build output in `build/`?"

**Answer:** Out-of-source builds keep source tree clean.

**Benefits:**
- `git status` stays clean (build/ in .gitignore)
- `rm -rf build` for clean rebuild
- Multiple build configs: `build-debug/`, `build-release/`

### "Can I build without Docker?"

**Answer:** Yes, but not recommended.

**Native build (advanced):**
1. Install GNURX toolchain
2. Install CMake
3. `mkdir build && cd build`
4. `cmake -DCMAKE_TOOLCHAIN_FILE=../cmake/toolchain-gnurx.cmake ..`
5. `make`

**Problem:** Your build might differ from teammates/CI

**Solution:** Use Docker for reproducibility

### "How do I add a new source file?"

**Answer:** Edit CMakeLists.txt, rebuild

```cmake
# In CMakeLists.txt:
set(SOURCES
    src/main.c
    src/hardware/startup_rx72n.S
    src/hardware/system_init.c
    src/hardware/gpio.c
    src/hardware/timer.c
    src/hardware/uart.c
    src/my_new_file.c        # <-- Add here
)
```

```bash
./build.sh                  # CMake detects change, rebuilds
```

## Comparison to Other Approaches

### Approach 1: All-in-Docker (Bad for Embedded)

```bash
# Build AND flash in Docker
docker run ... make flash
```

**Problems:**
- USB passthrough unreliable
- Different on Mac vs Linux vs Windows
- Debugger can't attach

### Approach 2: All-on-Host (Bad for Portability)

```bash
# Install GNURX on Mac, build natively
make
make flash
```

**Problems:**
- "Works on my machine" syndrome
- Different GCC versions across team
- Breaks when upgrading macOS

### Approach 3: Hybrid (Best - What We Use)

```bash
# Build in Docker (reproducible)
./build.sh

# Flash on host (hardware access)
./flash.sh
```

**Benefits:**
- Reproducible builds ✅
- Hardware access ✅
- Works on all platforms ✅
