\subsection{Motor Control Architecture}

\subsubsection{GPTW vs MTU Selection for PWM Generation}

The RX72N provides two timer peripherals suitable for motor control PWM generation: the General PWM Timer (GPTW) and the Multi-Function Timer Unit (MTU3a). After detailed analysis, \textbf{GPTW was selected} for the following technical reasons:

\textbf{Resolution and Performance:}
\begin{itemize}
    \item \textbf{GPTW:} 32-bit timer resolution enabling precise duty cycle control
    \item \textbf{MTU3a:} 16-bit timer resolution (65,536 maximum count)
    \item At 20 kHz PWM frequency with 120 MHz peripheral clock:
    \begin{itemize}
        \item GPTW provides 6,000 discrete duty cycle steps (120 MHz / 20 kHz)
        \item MTU limited to maximum 3,276 steps before counter overflow
    \end{itemize}
\end{itemize}

\textbf{Channel Architecture:}
\begin{itemize}
    \item \textbf{GPTW:} 4 independent channels, each with 2 complementary outputs (GTIOC0A/B through GTIOC3A/B)
    \item \textbf{Perfect match} for 4 motors in Phase/Enable (PH/EN) control mode
    \item Each motor driver (DRV8243S) requires exactly 2 PWM signals
\end{itemize}

\textbf{Peripheral Separation:}
\begin{itemize}
    \item Using GPTW for PWM and MTU for encoders provides clean functional separation
    \item MTU channels (MTU1/2/3/4) dedicated to encoder quadrature counting
    \item No resource conflicts between PWM generation and encoder reading
\end{itemize}

\textbf{Pin Flexibility:}
\begin{itemize}
    \item GPTW signals available on multiple pin locations via MPC (Multi-Function Pin Controller)
    \item Example: GTIOC0A available on pins 25, 65, 73, 83
    \item Enabled conflict-free allocation by selecting alternate pin groups
\end{itemize}

\subsubsection{Pin Allocation Strategy}

\textbf{Design Philosophy:}
\begin{enumerate}
    \item \textbf{Peripheral Grouping:} Place related functions on contiguous port pins
    \begin{itemize}
        \item GPTW PWM: PE0/1/5/6/7 and PA0/1/2 (logically grouped ports)
        \item SPI to RPi5: PA4-PA7 (4 adjacent pins for optimal PCB routing)
        \item MTU Encoders: P14-P15, P21-P27 (P2X port group)
        \item I2C/SMBUS: P12-P13 (RIIC0), P20-P21 (RIIC1)
    \end{itemize}

    \item \textbf{Conflict Resolution via Alternate Functions:}
    \begin{itemize}
        \item Initial pin selection caused conflicts between GPTW, I2C, and SPI
        \item Table 1.10 analysis revealed all peripherals have 2-4 alternate pin locations
        \item Moved GPTW from P17/P21-P23/PC6-PC7 to PE/PA ports
        \item Freed critical pins for I2C (P20-P21) and encoders (P22-P27)
    \end{itemize}

    \item \textbf{PCB Routing Optimization:}
    \begin{itemize}
        \item Contiguous pin blocks minimize trace crossings
        \item SPI signals on PA4-PA7 enable compact layout
        \item Motor control signals grouped by motor (PH + EN adjacent)
    \end{itemize}

    \item \textbf{Future Expandability:}
    \begin{itemize}
        \item 42 GPIO pins available after critical allocations
        \item Unused peripherals documented: Ethernet, QSPI, SDHI, additional SCI/RSPI channels
        \item Alternate pin functions reserved for hardware revisions
    \end{itemize}
\end{enumerate}

\subsubsection{Communication Bandwidth Analysis}

\textbf{SPI Configuration: 10 Mbps is Optimal}

Peak bandwidth calculation for RPi5 $\leftrightarrow$ RX72N communication:
\begin{itemize}
    \item \textbf{Velocity Commands (100 Hz):}
    \begin{itemize}
        \item Message size: 34 bytes (Nanopb encoded MotorVelocityCommand)
        \item Bandwidth: $34 \text{ bytes} \times 100 \text{ Hz} \times 8 = 27.2 \text{ Kbps}$
    \end{itemize}

    \item \textbf{Encoder Feedback (100 Hz):}
    \begin{itemize}
        \item Message size: 18 bytes (4 encoders $\times$ 4 bytes + header)
        \item Bandwidth: $18 \text{ bytes} \times 100 \text{ Hz} \times 8 = 14.4 \text{ Kbps}$
    \end{itemize}

    \item \textbf{Telemetry (50 Hz):}
    \begin{itemize}
        \item Message size: 64 bytes (battery, motor current, temperature, status)
        \item Bandwidth: $64 \text{ bytes} \times 50 \text{ Hz} \times 8 = 25.6 \text{ Kbps}$
    \end{itemize}

    \item \textbf{ARQ Protocol Overhead (estimated 40\%):}
    \begin{itemize}
        \item Headers: 8 bytes per frame (sequence, CRC-32, flags)
        \item Retransmissions: Average 5\% packet loss $\times$ 3 retry attempts
        \item Total overhead: $(27.2 + 14.4 + 25.6) \times 1.4 = 94.1 \text{ Kbps}$
    \end{itemize}
\end{itemize}

\textbf{Total Peak Bandwidth:}
$$\text{Peak} = 27.2 + 14.4 + 25.6 + 94.1 = \textbf{161.3 Kbps}$$

\textbf{SPI Utilization:}
$$\frac{161.3 \text{ Kbps}}{10 \text{ Mbps}} = \textbf{1.6\% utilization}$$

\textbf{Margin Analysis:}
\begin{itemize}
    \item Available headroom: $10,000 / 161.3 = 62\times$ current requirements
    \item No need for Ethernet (would add PHY chip, 9+ pins, PCB complexity)
    \item No need for QSPI (RPi5 doesn't support quad-lane SPI natively)
    \item 10 Mbps provides excellent margin for future features (camera data, additional sensors)
\end{itemize}
