\subsection{Transport Priority}

USB CDC is the \textbf{primary} transport and SPI is the \textbf{backup}. Priority values are defined in \texttt{star-gateway/internal/manager/types.go}:

\begin{lstlisting}[language=Go, caption={Transport Priority Constants}]
PriorityUSB = 10  // higher = preferred
PrioritySPI = 5
\end{lstlisting}

The \texttt{TransportManager} selects the highest-priority healthy transport at runtime. USB is preferred for three reasons:

\begin{itemize}[leftmargin=1.5em,topsep=4pt,itemsep=2pt]
    \item \textbf{Lower latency:
}
0.5 --1\, ms(USB) vs 1 --2\, ms(SPI)
    \item \textbf{Hardware CRC and bulk retries :} Built into the USB protocol
    ,
    making application - level HARQ redundant on this path
    \item \textbf{Simplified software :} No ACK / NACK handshake
        or FEC codec overhead required
\end{itemize}

        SPI enables full HARQ(per ADR - 001) because it lacks USB's built-in reliability mechanisms. A shared \texttt{SessionState} (TX/RX sequence counters) spans both transports, preventing sequence desynchronization during failover. Both USB and SPI increment the same sequence counter.

\subsection{Protocol Primer
}
\label{subsec:protocol-primer}

This subsection explains each protocol building block from first principles. Understanding these concepts is essential for working on any part of the communication stack.

\subsubsection{CRC-32 (Cyclic Redundancy Check)}

A CRC-32 is a 4-byte ``fingerprint'' computed over a block of data. The sender computes the CRC over the frame contents and appends it;
the receiver recomputes the CRC over the same data and compares.If even a single
    bit flipped during transmission,
    the CRCs will not match and the receiver knows the frame is corrupt.

\textbf{How it works:
}
\begin{enumerate}[leftmargin = 1.5em, topsep = 4pt, itemsep = 2pt]
    \item Treat the data bytes as a long binary polynomial
        .
    \item Divide this polynomial by a fixed \emph{
            generator polynomial}(IEEE 802.3
                                  : \texttt{0x04C11DB7})
        .
    \item The 32 -
    bit remainder is the CRC.Append it to the frame
        .
    \item The receiver performs the same division.If the remainder is zero,
    the frame is intact.
\end{enumerate}

\textbf{Properties:
}
\begin{itemize}[leftmargin = 1.5em, topsep = 4pt, itemsep = 2pt]
    \item \textbf{Detection only, not correction :
} CRC tells you \emph{something} is wrong,
    but not \emph{what} or \emph{where}.If a CRC fails,
    the only option is to discard the frame and request retransmission
            .
    \item \textbf{Detects all single - bit, double - bit,
                   and odd -
                       bit errors.} Detects all burst errors up to 32 bits.
    \item \textbf{Hardware - accelerated on the RX72N :
           } The CRC Calculator peripheral computes CRC -
        32 in hardware,
    avoiding CPU overhead.
    \item \textbf{Used on every frame :} Both USB CDC and SPI frames include CRC-32,
    regardless of whether HARQ is enabled.
\end{itemize}

\noindent\colorbox{keyinsightcolor} {
  \parbox{\dimexpr\linewidth - 2\fboxsep} {
    %
\textbf{Analogy :} CRC is like a check digit on a credit card
                number.It catches typos instantly but cannot fix them-- -
        you have to re - enter the number.
 }
}

\subsubsection{ARQ(Automatic Repeat Request)}

    ARQ is the simplest reliability mechanism : if a frame arrives
                                                corrupted(CRC fails) or
                                                does not arrive at all(timeout),
    the receiver asks the sender to retransmit.This is \textbf{error detection +
                                                               retransmission},
    not error correction.

\textbf{Protocol flow:
}
\begin{enumerate}[leftmargin = 1.5em, topsep = 4pt, itemsep = 2pt]
    \item Sender transmits frame with \texttt{REQUIRES\_ACK} flag set
    .
    \item Sender starts a
    timer(10\, ms timeout in STAR)
    .
    \item Receiver validates CRC :
    \begin{itemize}
\item CRC valid $\rightarrow$ send \textbf{ACK}(positive acknowledgment)
    .
        \item CRC invalid $\rightarrow$ send \textbf{NACK}(negative acknowledgment)
    .
    \end{itemize}
\item Sender receives response :
    \begin{itemize}
\item ACK $\rightarrow$ success, move to next frame
                                     .
        \item NACK $\rightarrow$ retransmit the same
                                     frame(set \texttt{RETRANSMIT} flag)
                                     .
        \item Timeout $\rightarrow$ retransmit(assume frame was lost)
                                     .
    \end{itemize}
\item After 3 failed retries, declare the link failed.
\end{enumerate}

\textbf{Limitation:
} Pure ARQ wastes the corrupted frame entirely. If 99\% of the bits arrived correctly and 1\% were wrong, ARQ discards all of it and retransmits from scratch. This is where FEC comes in.

\subsubsection{FEC (Forward Error Correction)}

FEC adds \emph{redundant} data to the transmission so the receiver can \textbf{correct} errors without retransmission. The idea is simple: send more bits than strictly necessary, so that even if some are corrupted, the original data can be recovered mathematically.

\textbf{Everyday analogy:} If you spell out a phone number as ``five-five-five, one-two-three-four'', someone hearing ``five-five-STATIC-one-two-three-four'' can guess the missing digit because they know phone numbers are 7 digits and the pattern is obvious. FEC formalizes this intuition.

\textbf{STAR uses convolutional coding}, a specific FEC technique:

\begin{itemize}[leftmargin=1.5em,topsep=4pt,itemsep=2pt]
    \item \textbf{Constraint length $K=7$:} The encoder has a 6-bit shift register (memory), so each output bit depends on the current input bit and the 6 previous input bits. This creates complex relationships between bits that the decoder can exploit.
    \item \textbf{Rate $1/2$:} For every 1 input bit, the encoder produces 2 output bits. This means the encoded data is exactly 2$\times$ the size of the original, doubling bandwidth usage in exchange for error correction capability.
    \item \textbf{Generator polynomials:} $G_1 = 171_8$ (\texttt{0x79}) and $G_2 = 133_8$ (\texttt{0x5B}). These are NASA standard polynomials used in deep-space communication, chosen for their optimal distance properties.
\end{itemize}

\textbf{Encoding process:}
\begin{enumerate}[leftmargin = 1.5em, topsep = 4pt, itemsep = 2pt]
    \item Each input bit shifts into a 6 - stage register.
    \item Two output bits are produced by XOR -
    ing specific register taps(determined by $G_1$ and $G_2$).
    \item A 100 - byte payload becomes a 200 -
    byte encoded payload plus tail bits.
\end{enumerate}

\subsubsection{Viterbi Decoder (Soft-Decision)}

The Viterbi algorithm is the standard method for decoding convolutional codes. It finds the \emph{most likely} original data sequence given a noisy received signal.

\textbf{Hard bits vs.\ soft bits:
}
\begin{itemize}[leftmargin = 1.5em, topsep = 4pt, itemsep = 2pt]
    \item \textbf{Hard bits :} Binary 0 or
    1. No confidence information. ``The bit is 1.''
    \item \textbf{Soft bits :} A signed value from $ - 127 $ to $ +
        127 $(stored as \texttt{int8\_t})
            .The sign indicates the likely bit
        value(negative = likely 0, positive = likely 1),
    and the \emph{magnitude} indicates confidence.For example :
    \begin{itemize}
\item $ + 127 $ = ``very confident this is a 1''
        \item $ + 10 $ = ``probably a 1, but not sure''
        \item $ - 127 $ = ``very confident this is a 0''
        \item $0$ = ``complete erasure, no idea''
    \end{itemize}
\end{itemize}

\textbf{Why soft bits matter :} Soft -
    decision decoding provides approximately 2\,
    dB gain over hard -
        decision decoding.This means the decoder can correct more errors because
            it uses \emph{confidence} information,
    not just guesses.

\textbf{Viterbi algorithm overview:
}
\begin{enumerate}[leftmargin=1.5em,topsep=4pt,itemsep=2pt]
    \item The encoder can be modeled as a state machine with $2^{
  K - 1} = 64$ states (for $K=7$).
    \item At each time step, the decoder computes the ``distance'' (error metric) between the received soft bits and what each possible state transition would have produced.
    \item It keeps only the best path (lowest cumulative error) into each state --- this is the ``survivor path.''
    \item After processing all received bits, the decoder traces back through the survivor paths to find the most likely original bit sequence.
\end{enumerate}

\subsubsection{HARQ(Hybrid Automatic Repeat Request)}

HARQ is \textbf{not a separate protocol
} --- it is the \textbf{combination} of ARQ and FEC working together. The key insight is that each mechanism compensates for the other's weakness:

\begin{itemize}[leftmargin=1.5em,topsep=4pt,itemsep=2pt]
    \item \textbf{ARQ alone:} Discards corrupted frames entirely, wastes bandwidth retransmitting data that was mostly correct.
    \item \textbf{FEC alone:} Can correct limited errors but cannot request retransmission if corruption is too severe.
    \item \textbf{HARQ (both):} FEC corrects minor errors in-place. If corruption exceeds FEC capability, ARQ requests retransmission. On retransmission, Chase Combining accumulates evidence from both attempts for even better decoding.
\end{itemize}

\subsubsection{Chase Combining(Type I HARQ)}

    Chase Combining is the mechanism that makes retransmissions \emph{
        more valuable} than just sending the same data again.Instead of
        discarding the failed frame and using only the retransmitted copy,
    Chase Combining \textbf{accumulates soft -
                            bit observations} from every transmission attempt.

\textbf{How it works:
}
\begin{enumerate}[leftmargin=1.5em,topsep=4pt,itemsep=2pt]
    \item \textbf{First transmission:} Receiver gets soft bits (e.g., $[+80, -30, +5, -120, \ldots]$). CRC fails.
    \item \textbf{Receiver stores soft bits} in an \texttt{int16} accumulator array (not discarded!).
    \item \textbf{Retransmission:} Receiver gets new soft bits for the same data (e.g., $[+60, -90, +40, -100, \ldots]$).
    \item \textbf{Combine:} Add element-wise: $[+80+60, -30+(-90), +5+40, -120+(-100), \ldots] = [+127, -120, +45, -127, \ldots]$.
    \item \textbf{Clamp} combined values to $[-127, +127]$ (int8 range) and feed to Viterbi decoder.
    \item Bits where both transmissions agreed become \emph{more confident} (higher magnitude). Bits where they disagreed partially cancel, correctly reflecting uncertainty.
\end{enumerate}

\textbf{Gain :} Each additional transmission provides approximately 3\,
    dB of combining
        gain.Two transmissions combined can correct errors that neither could
            individually.After 3 transmissions with combining,
    the system achieves roughly 4 --5\,
    dB total coding gain over a single attempt.

\subsubsection{USB CDC(Communications Device Class)}

USB CDC is a standard USB device class that creates a \textbf{virtual serial port} over USB.When the RX72N is plugged into the Raspberry
    Pi 5 via USB,
    the Linux kernel automatically creates a \texttt{
        / dev / ttyACM0} device that applications can read /
        write like a regular serial port.

\textbf{Why USB CDC needs no HARQ:
}
\begin{itemize}[leftmargin=1.5em,topsep=4pt,itemsep=2pt]
    \item \textbf{Hardware CRC-16:} Every USB packet (max 64 bytes for Full-Speed) includes a 16-bit CRC computed and verified by the USB hardware controller. Corrupted packets are automatically discarded at the hardware level.
    \item \textbf{Automatic bulk retries:} USB bulk transfers automatically retry failed packets up to 3 times at the hardware level, transparent to software. The application never sees the retransmission.
    \item \textbf{Differential signaling:} USB uses a twisted differential pair (D+/D-), which provides inherent common-mode noise rejection. This makes bit errors extremely rare compared to single-ended SPI.
    \item \textbf{Handshake protocol:} Every bulk transfer includes a three-phase handshake (TOKEN $\rightarrow$ DATA $\rightarrow$ HANDSHAKE), ensuring reliable delivery.
\end{itemize}

\textbf{What STAR's CDCLink does provide:}
\begin{itemize}[leftmargin=1.5em,topsep=4pt,itemsep=2pt]
    \item Application-level CRC-32 (end-to-end integrity, covering the full frame including header).
    \item Sequence number tracking via shared \texttt{SessionState}.
    \item Gap tolerance (accepts sequence gaps $< 10$ frames for rare USB packet loss).
    \item Send serialization via \texttt{sendMutex} (prevents out-of-order transmission).
    \item Send timeout protection (50\,ms timeout prevents blocking on USB disconnect).
\end{itemize}

  \subsubsection{SPI(Serial Peripheral Interface)}

      SPI is a synchronous 4 -
      wire bus connecting the Raspberry Pi 5(Controller)to the RX72N(Peripheral)
          .Unlike USB,
      SPI is a raw electrical interface with \textbf{zero built - in error detection or correction}
          .

\textbf{SPI wires:
 }
  \begin{itemize}[leftmargin = 1.5em, topsep = 4pt, itemsep = 2pt]
    \item \textbf{SCLK :} Clock signal(10\, MHz),
      driven by the RPi5 Controller.
    \item \textbf{COPI :} Controller Out,
      Peripheral In(data from RPi5 to RX72N).
    \item \textbf{CIPO :} Controller In,
      Peripheral Out(data from RX72N to RPi5)
          .
    \item \textbf{CS :} Chip Select(active low, selects the RX72N)
          .
\end{itemize}

  \textbf{Why SPI needs full HARQ:}
  \begin{itemize}[leftmargin = 1.5em, topsep = 4pt, itemsep = 2pt]
    \item \textbf{No hardware CRC :
 } SPI shifts raw bits.A single bit flip from EMI or
      crosstalk passes through silently unless the application checks.
    \item \textbf{No retransmission :} SPI is fire -
          and-forget.If a byte is corrupted,
      there is no hardware mechanism to request it again.
    \item \textbf{Single - ended signaling :} SPI lines are not differential,
      making them more susceptible to electromagnetic interference(EMI)
          from nearby motor drivers,
      switched power supplies,
      and PWM signals.
    \item \textbf{Motor environment:}
      The STAR robot runs 4 brushed DC motors with 4x \texttt{DRV8263H}
      H-bridge drivers. PWM switching at 20\,kHz generates
      significant EMI that can couple into SPI traces.
\end{itemize}

  \textbf{STAR's SPI protection stack:}

\begin{enumerate}[leftmargin = 1.5em, topsep = 4pt, itemsep = 2pt]
    \item \textbf{CRC - 32 :
   } Detects corruption(every frame)
                           .
    \item \textbf{FEC encoding :} Adds redundancy (rate 1/2 convolutional code).
    \item \textbf{ACK / NACK :} Requests retransmission if FEC cannot correct.
    \item \textbf{Chase Combining :} Accumulates soft bits across
            retransmissions.
    \item \textbf{Viterbi decoding :
           } Finds most likely original data from combined soft bits.
\end{enumerate}

\subsection{Reliability: SPI HARQ Send/Receive Paths}

\subsubsection{SPI Send Path (HARQ)}

When the gateway sends a command over SPI, the following pipeline executes:

\begin{enumerate}[leftmargin=1.5em,topsep=4pt,itemsep=2pt]
    \item \texttt{SPILink.Send()} acquires the send mutex (atomic sequence assignment).
    \item Payload is FEC-encoded: convolutional encoder produces 2$\times$ the input size.
    \item Frame is built: SYNC + header (with \texttt{REQUIRES\_ACK} and \texttt{FEC\_ENABLED} flags) + encoded payload + CRC-32.
    \item Frame is transmitted over SPI via \texttt{transport.Send()}.
    \item \texttt{SPILink} starts a 10\,ms ACK timer and waits.
    \item If ACK received: success, return to caller.
    \item If NACK received or timeout:
    \begin{enumerate}
        \item Increment retry counter.
        \item Set \texttt{RETRANSMIT} flag in header.
        \item Retransmit the same encoded frame.
        \item Wait for ACK again (up to 3 total attempts).
    \end{enumerate}
    \item After 3 failures: return error, trigger health monitor.
\end{enumerate}

\subsubsection{SPI Receive Path (Chase Combining + Viterbi)}

When the RX72N receives a frame on SPI:

\begin{enumerate}[leftmargin=1.5em,topsep=4pt,itemsep=2pt]
    \item \texttt{rx\_spi\_link\_receive()} reads raw bytes from \texttt{rx\_spi\_comm}.
    \item If \texttt{FEC\_ENABLED} flag is set:
    \begin{enumerate}
        \item Convert raw bytes to soft bits: each byte produces 8 soft bits using MSB-first extraction, mapping hard 0 $\rightarrow -127$ and hard 1 $\rightarrow +127$.
        \item Feed soft bits to \texttt{rx\_harq\_decode()}.
        \item If \texttt{RETRANSMIT} flag is set, the HARQ module performs Chase Combining: adds new soft bits to the accumulator from the previous attempt, then clamps to $[-127, +127]$.
        \item Run Viterbi decoder on the combined soft bits.
        \item Check decoded CRC:
        \begin{itemize}
            \item CRC valid $\rightarrow$ send ACK, deliver decoded payload to application.
            \item CRC invalid $\rightarrow$ send NACK, keep accumulator for next retry.
        \end{itemize}
    \end{enumerate}
    \item If FEC disabled: standard CRC-32 validation only.
\end{enumerate}

\subsubsection{USB CDC Path: No HARQ}

USB CDC does not require application-level HARQ. The USB hardware provides CRC-16 on every packet and automatic bulk retry on error, making ARQ and FEC redundant. The \texttt{CDCLink} implementation (\texttt{internal/link/cdc.go} and \texttt{libs/rx\_usb\_comm/}) contains \textbf{zero references} to HARQ, FEC, Viterbi, or Chase Combining code.

\subsection{Safety Features}

\begin{itemize}[leftmargin=1.5em,topsep=4pt,itemsep=2pt]
    \item \textbf{Communication watchdog (500\,ms):} The RX72N triggers an emergency stop if no valid frame is received within 500\,ms, ensuring the robot halts on link failure.
    \item \textbf{Duplicate detection:} Shared \texttt{SessionState} sequence numbers detect and discard duplicate frames across both transports.
    \item \textbf{CRC-32 (IEEE 802.3):} Every frame is protected by CRC-32, hardware-accelerated on the RX72N CRC Calculator peripheral.
    \item \textbf{Failover continuity:} Shared \texttt{SessionState} prevents sequence desynchronization during USB$\leftrightarrow$SPI failover.
    \item \textbf{Atomic sequence assignment:} A \texttt{sendMutex} ensures that sequence number assignment and frame transmission are atomic, preventing out-of-order frames from concurrent goroutines.
\end{itemize}

\vspace{0.2cm}

\noindent\colorbox{importantcolor}{\parbox{\dimexpr\linewidth-2\fboxsep}{%
\textbf{Important:} The 500\,ms communication watchdog is the last line of defense. If all transports fail and no valid frame arrives within this window, the RX72N immediately disables all motor outputs and enters the emergency stop state. Recovery requires an explicit reset command after communication is restored.
