\section{Communication Stack}

\subsection{Overview}

The STAR platform uses two independent communication paths between the
Raspberry Pi 5 and the RX72N motor controller. Both carry the same
frame-level protocol described in \S\ref{section:nanopb-protocol}; they are
dedicated to different host-side consumers rather than acting as redundant
failover paths for the same consumer.

\begin{center}
\begin{tabular}{|l|l|l|l|}
\hline
\textbf{Path}      & \textbf{Host consumer}                & \textbf{Link}                                      & \textbf{Rate} \\
\hline
UART-over-USB      & \texttt{star-gateway} (Go, gRPC / WS) & SCI9 $\rightarrow$ CY7C65213 $\rightarrow$ ttyUSB0 & 921\,600 baud \\
SPI                & \texttt{star\_spi\_bridge} (ROS2)      & RSPI2 $\rightarrow$ spidev0.0                       & 10\,MHz clock \\
\hline
\end{tabular}
\end{center}

The RX72N's native USB peripheral (USB0) has been removed. It formerly
enumerated multiple virtual COM ports on the same USB connector; that entire
driver stack is gone. Only the two paths above remain.

\subsection{Why Two Paths}

\begin{itemize}
  \item The gateway needs a plug-and-play transport suited to human-paced
        command / telemetry traffic (WebSocket clients, CLI tools, gRPC
        integration tests). UART-over-USB is both simple and resilient
        thanks to the CY7C65213 bridge chip absorbing USB framing quirks.
  \item The ROS2 motor-control node needs sub-millisecond, jitter-bounded
        round-trips for closed-loop velocity control at 100\,Hz on four
        wheels. SPI is the right fit; it also permits hardware FEC and
        Chase Combining under the PWM-noisy motor environment.
\end{itemize}

\subsection{Layers}

\begin{center}
\begin{tabular}{|c|l|l|}
\hline
\textbf{Layer} & \textbf{Responsibility}                     & \textbf{Implementation} \\
\hline
5 Application  & Command handlers, telemetry aggregation      & Gateway services, ROS2 nodes \\
4 Serialization& Protocol Buffers                             & generated Go / C++ / nanopb \\
3 Link (SPI)   & FEC + Chase Combining, ARQ retries          & \texttt{rx\_spi\_link}, gateway FEC \\
2 Framing      & SYNC + SEQ + LEN + TYPE + FLAGS + CRC-32    & \texttt{rx\_frame}, \texttt{internal/frame} \\
1 Transport    & UART @ 921\,600 or SPI @ 10\,MHz             & \texttt{rx\_uart\_comm}, \texttt{rx\_spi\_comm} \\
\hline
\end{tabular}
\end{center}

The UART path skips the Layer-3 link layer because the CY7C65213 plus USB
CDC driver on the host already provides lossless, in-order byte delivery;
the framing-layer CRC is enough. The SPI path uses the full link layer
because SPI itself is ECC-free and sensitive to motor-driver EMI.

\subsection{Log Multiplexing on UART}

The UART byte stream carries both protobuf frames and firmware runtime logs,
distinguished by the TYPE byte:

\begin{itemize}
  \item TYPE $\in \{0x10, 0x11, 0xFF, \ldots\}$: application or control
        frames, payload is protobuf-encoded or empty.
  \item TYPE $= 0x20$ (\texttt{LOG\_MESSAGE}): payload is ASCII log text
        emitted by the RX72N's \texttt{rx\_log\_*} macros. The gateway
        extracts the payload and writes it to its own log stream with a
        \texttt{[RX72N]} prefix.
\end{itemize}

There is no risk of the sync word \texttt{0x55AA} appearing inside log text
and fooling the decoder because log bytes never leave the framing layer as
raw bytes -- every log chunk is a complete, CRC-checked frame.
