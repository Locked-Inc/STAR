\section{ROS2 Integration and Sensor Fusion Architecture}

\subsection{Overview}

The STAR platform utilizes ROS2 Jazzy Jalisco as the primary high-level orchestration layer. The integration strategy focuses on providing a modular, reliable, and deterministic environment for SLAM, navigation, and mission control. This section details the architecture for Visual-LiDAR sensor fusion, coordinate frame definitions, and custom node interfaces.

\subsection{Visual-LiDAR Sensor Fusion with RTAB-Map}

The platform implements a heterogeneous sensor fusion strategy combining geometric data from LiDAR and appearance-based data from an RGB-D camera using \textbf{RTAB-Map} (Real-Time Appearance-Based Mapping).

\subsubsection{Fusion Architecture}
The fusion process is divided into two main layers:
\begin{enumerate}
    \item \textbf{Local State Estimation (EKF):} The \texttt{robot\_localization} package runs an Extended Kalman Filter (EKF) fusing:
    \begin{itemize}
        \item Wheel Odometry (from RX72N via \texttt{star\_spi\_bridge})
        \item IMU Linear Acceleration and Angular Velocity (from OAK-D or dedicated IMU)
    \end{itemize}
    \item \textbf{Global SLAM and Loop Closure (RTAB-Map):} The \texttt{rtabmap\_ros} node consumes:
    \begin{itemize}
        \item Laser Scan data from RPLiDAR C1.
        \item RGB-D images and PointClouds from the OAK-D camera.
        \item Filtered Odometry from the EKF.
    \end{itemize}
\end{enumerate}

\subsubsection{Mapping Strategy}
RTAB-Map performs loop closure detection using a bag-of-words approach. When a loop is detected, it optimizes the pose graph to minimize drift. The resulting map is published as a 2D occupancy grid for Nav2 and a 3D octomap for obstacle avoidance.

\subsection{Coordinate Frames (REP-105)}

The STAR platform adheres to the \textbf{REP-105} standard for coordinate frames. The transform tree (\texttt{tf2}) is structured as follows:

\begin{itemize}
    \item \textbf{\texttt{map}:} The global coordinate frame. Fixed to the world.
    \item \textbf{\texttt{odom}:} The local coordinate frame. Drift-prone, but continuous. The \texttt{map} $\rightarrow$ \texttt{odom} transform is published by RTAB-Map (Loop Closure).
    \item \textbf{\texttt{base\_link}:} The center of the robot's drive axis. The \texttt{odom} $\rightarrow$ \texttt{base\_link} transform is published by the EKF.
    \item \textbf{\texttt{laser\_frame}:} The reference frame for the RPLiDAR C1.
    \item \textbf{\texttt{camera\_link}:} The reference frame for the OAK-D Depth Camera.
\end{itemize}

\subsection{Custom ROS2 Nodes and Interfaces}

Three primary custom nodes facilitate the interaction between the STAR hardware and the ROS2 ecosystem.

\subsubsection{\texttt{star\_spi\_bridge}}
Bridges the low-level SPI protocol (RX72N) to ROS2 topics.
\begin{itemize}
    \item \textbf{Subscribed Topics:} \texttt{/cmd\_vel} (geometry\_msgs/Twist)
    \item \textbf{Published Topics:} \texttt{/odom/unfiltered} (nav\_msgs/Odometry), \texttt{/joint\_states} (sensor\_msgs/JointState)
    \item \textbf{Parameters:} \texttt{spi\_device}, \texttt{spi\_speed\_hz}, \texttt{gear\_ratio}
\end{itemize}

\subsubsection{\texttt{star\_gateway\_bridge}}
Provides a bridge between the gRPC/WebSocket gateway and the ROS2 computational graph.
\begin{itemize}
    \item \textbf{Subscribed Topics:} \texttt{/robot\_status}, \texttt{/battery\_state}
    \item \textbf{Published Topics:} \texttt{/teleop/cmd\_vel} (overrides for manual control)
    \item \textbf{Services:} \texttt{/set\_pid\_gains}, \texttt{/trigger\_calibration}
\end{itemize}

\subsubsection{\texttt{star\_safety\_monitor}}
Ensures platform integrity and manages emergency states.
\begin{itemize}
    \item \textbf{Logic:} Monitors battery voltage, motor current, and heartbeat from the RPi5 and RX72N.
    \item \textbf{Actions:} Publishes \texttt{/emergency\_stop} or resets the motor controller if a timeout occurs.
\end{itemize}

\subsection{Multi-Machine Communication}

To ensure isolation and prevent interference in multi-robot environments, the \texttt{ROS\_DOMAIN\_ID} environment variable must be set uniquely for each STAR unit (e.g., \texttt{export ROS\_DOMAIN\_ID=42}). 

\subsection{Hardware Persistence (udev rules)}

Consistent device naming is critical for reliable startup. The following \texttt{udev} rules are required in \texttt{/etc/udev/rules.d/99-star.rules}:

\begin{verbatim}
# RPLiDAR C1
SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", SYMLINK+=/dev/ttyLidar"
# RX72N Motor Controller (via USB-Serial if applicable, or SPI identification)
SUBSYSTEM=="spidev", KERNEL=="spidev0.0", GROUP=="spi", MODE=="0660"
\end{verbatim}
