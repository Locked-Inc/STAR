\section{Firmware Gaps (RX72N)}
\label{sec:firmware}

The RX72N firmware has excellent core implementation -- all 9 ThreadX tasks are complete, all hardware drivers work, and the HARQ/FEC/CRC-32 communication stack is production-ready. The missing piece is the \textbf{integration layer} between the communication task and application tasks.

\begin{longtable}{L{5cm} L{1.8cm} L{2cm} L{5cm}}
\toprule
\textbf{Gap} & \textbf{Severity} & \textbf{Effort} & \textbf{Impact} \\
\midrule
WireMessage dispatcher & \critical & 4--6 hrs & ALL RPi5 commands blocked \\
OTA firmware update handler & \high & 2--3 days & Firmware updates blocked \\
NVS configuration persistence & \high & 4--6 hrs & PID settings lost on reboot \\
BMS telemetry integration & \medium & 4--6 hrs & Battery status invisible \\
RPLiDAR C1 integration & \low & 2--3 days & SLAM impossible \\
Host I2C (RIIC0) application & \low & 1--2 days & Future sensor expansion \\
\bottomrule
\end{longtable}

\subsection{Gap 1: WireMessage Dispatcher (CRITICAL)}

The \texttt{comm\_task.c} receives SPI/USB frames, decodes them via nanopb, but has \textbf{no dispatch logic} to route the decoded \texttt{star\_v1\_WireMessage} to the correct handler. Every command from the RPi5 is silently dropped.

\begin{lstlisting}[language=C, caption={Required dispatcher implementation in comm\_task.c}]
static rx_err_t internal_dispatch_wire_message(
    const star_v1_WireMessage* msg)
{
    RX_CHECK_NULL_PTR(msg, k_rx_err_null_ptr);

    switch (msg->which_payload) {
    case star_v1_WireMessage_velocity_command_tag:
        return motor_control_handle_velocity_command(
            &msg->payload.velocity_command);

    case star_v1_WireMessage_emergency_stop_command_tag:
        return motor_control_handle_emergency_stop(
            &msg->payload.emergency_stop_command);

    case star_v1_WireMessage_pid_config_tag:
        return config_handle_pid_update(&msg->payload.pid_config);

    case star_v1_WireMessage_retransmit_config_tag:
        return config_handle_retransmit_update(
            &msg->payload.retransmit_config);

    default:
        rx_log_warn(k_tag_comm, "Unknown WireMessage type: %d",
                    (int)msg->which_payload);
        return k_rx_ok;  /* Forward compatible -- not fatal */
    }
}
\end{lstlisting}

Handler signatures required in task headers:
\begin{lstlisting}[language=C, caption={New public API in motor\_control\_task.h}]
rx_err_t motor_control_handle_velocity_command(
    const star_v1_VelocityCommand* cmd);
rx_err_t motor_control_handle_emergency_stop(
    const star_v1_EmergencyStopCommand* cmd);
rx_err_t motor_control_handle_power_command(
    const star_v1_MotorPowerCommand* cmd);
\end{lstlisting}

\textbf{Required Unity tests} (\texttt{tests/test\_comm\_task\_dispatch.c}):
\begin{itemize}[noitemsep]
  \item Velocity command routes to motor handler
  \item E-Stop command routes with highest priority
  \item Unknown type logs warning but does not crash
  \item NULL message returns \texttt{k\_rx\_err\_null\_ptr}
  \item PID config routes to config handler
\end{itemize}

\subsection{Gap 2: OTA Firmware Update Handler (HIGH)}

The Gateway has 10 RPC methods for OTA firmware update -- all return \texttt{codes.Unimplemented}. The firmware has no OTA handler. The RX72N has dual-bank flash (documented in PR \#305 linker fix), enabling live OTA.

Required state machine:

\begin{lstlisting}[language=C, caption={OTA state machine types}]
typedef enum : uint8_t {
    k_ota_state_idle        = 0, /**< No update in progress */
    k_ota_state_starting    = 1, /**< BeginUpdate received */
    k_ota_state_receiving   = 2, /**< WriteChunk frames arriving */
    k_ota_state_validating  = 3, /**< Checking CRC-32 + size */
    k_ota_state_ready       = 4, /**< Validated, ready to reboot */
    k_ota_state_error       = 5, /**< Error occurred */
} ota_state_t;
\end{lstlisting}

New library required: \texttt{e2-studio-star-rx72n-firmware/libs/rx\_ota/}

\subsection{Gap 3: NVS Configuration Persistence (HIGH)}

PID gains and system configuration are received but not saved. On reboot all tuned parameters are lost. The RX72N has 64KB Data Flash (separate from code flash) ideal for NVS.

\begin{lstlisting}[language=C, caption={Required NVS API (libs/rx\_nvs/inc/rx\_nvs.h)}]
rx_err_t rx_nvs_write(const char* key, const void* data, uint16_t len);
rx_err_t rx_nvs_read(const char* key, void* data, uint16_t* len);
rx_err_t rx_nvs_delete(const char* key);
rx_err_t rx_nvs_erase_all(void);  /* Factory reset */
\end{lstlisting}

\subsection{Gap 4: BMS Telemetry Integration (MEDIUM)}

The \texttt{bms\_monitor\_task} correctly detects battery faults and triggers E-Stop via IRQ13, but the BMS data (SOC, cell voltage, current) is \textbf{not included in the telemetry protobuf} sent to the RPi5. The operator cannot see battery state.

Required additions to \texttt{bms\_monitor\_task.h}:
\begin{lstlisting}[language=C, caption={Thread-safe BMS getter API}]
uint32_t bms_get_voltage_mv(void);
uint32_t bms_get_current_ma(void);
uint8_t  bms_get_soc_percent(void);
int16_t  bms_get_temperature_deci_celsius(void);
bool     bms_is_charging(void);
uint32_t bms_get_fault_flags(void);
\end{lstlisting}

\subsection{Gap 5: RPLiDAR C1 Integration (LOW -- deferred)}

The RPLiDAR C1 is in the project hardware list but has zero firmware integration. Required: UART driver library (\texttt{libs/rx\_rplidar/}), task (\texttt{lidar\_scan\_task.c}), pin assignment (SCI1 or SCI2), and LiDAR scan data in telemetry proto. \textbf{Estimated effort: 2--3 days.}

\subsection{Gap 1: FirmwareUpdateService (CRITICAL, 0\% Complete)}

All 10 RPC methods in \texttt{internal/service/firmware.go} follow this pattern:

\begin{lstlisting}[language={[GNU]C++}, caption={Current state of firmware.go -- all methods unimplemented}]
func (s *FirmwareService) BeginUpdate(ctx context.Context,
    req *starv1.BeginUpdateRequest) (*starv1.BeginUpdateResponse, error) {
    // TODO: Implement BeginUpdate
    return nil, status.Error(codes.Unimplemented, "not implemented")
}
\end{lstlisting}

Affected RPCs: \texttt{BeginUpdate}, \texttt{WriteChunk}, \texttt{StreamChunks}, \texttt{FinalizeUpdate}, \texttt{AbortUpdate}, \texttt{GetUpdateProgress}, \texttt{StreamUpdateProgress}, \texttt{Reboot}, \texttt{Rollback}, \texttt{MarkValid}.

Required Go session management:
\begin{lstlisting}[language={[GNU]C++}, caption={Session management struct for OTA}]
type otaSession struct {
    sessionID    string
    totalSize    uint64
    bytesWritten uint64
    expectedCRC  uint32
    startTime    time.Time
    mu           sync.Mutex
}
\end{lstlisting}

Also requires addition of \texttt{FirmwareChunk} to \texttt{wire.proto} WireMessage oneof (see Section~\ref{sec:proto}).

\subsection{Gap 2: E-Stop Priority Framing (HIGH)}

Emergency stop commands use \texttt{PriorityNormal} in the HARQ layer. Under heavy telemetry load, an E-Stop could be delayed by queued normal frames -- a safety hazard.

\textit{Fix:} Add \texttt{PriorityEmergency} constant to the HARQ client and use it in \texttt{EmergencyStop()} method.

\subsection{Gap 3: SetPIDGains Silently Dropped (HIGH)}

\texttt{gateway\_service.go:205} has a TODO: ``Forward to ROS2 service when available.'' Currently PID gain changes from the UI are accepted but never forwarded to the firmware. \textit{Fix:} Send a \texttt{PidConfig} WireMessage directly via HARQ to the RX72N.

\subsection{Gap 1: star\_spi\_bridge Hardware Testing (CRITICAL)}

The code is written (420-line lifecycle node + 152-line SPI driver + 397-line tests) but has \textbf{never been run on real hardware} (RPi5 + RX72N). This is the critical path for first robot motion.

\textbf{Hardware test commands:}
\begin{lstlisting}[language=bash, caption={SPI bridge hardware validation procedure}]
# On RPi5 with ROS2 Jazzy:
cd /workspaces/STAR/star-ros2
colcon build --packages-select star_spi_bridge

source install/setup.bash
ros2 launch star_spi_bridge star_spi_bridge.launch.py

# In second terminal -- send velocity command:
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist \
    "linear: {x: 0.1}" --rate 10 --times 30

# Verify encoder feedback:
ros2 topic echo /odom/unfiltered --once
ros2 topic hz /joint_states  # Expected: ~100 Hz
\end{lstlisting}

\textbf{Known risks:} SPI device path (\texttt{/dev/spidev0.0} vs \texttt{/dev/spidev0.1}), SPI mode mismatch, CRC byte order.

\subsection{Gap 2: Zero-Velocity Safety Shutdown (HIGH)}

\texttt{star\_spi\_driver\_node.cpp:112} has TODO: ``Send final zero-velocity frame before deactivation.'' If the ROS2 node crashes, motors continue at their last commanded velocity -- a critical safety issue.

\textbf{Fix location:} \texttt{StarSpiDriverNode::on\_deactivate()} -- send zero velocity frame with 3 retry attempts before deactivating publishers.

\subsection{Gap 3: star\_bringup Launch Files (HIGH, 5\% Complete)}

The \texttt{star\_bringup} package is an empty skeleton. Without launch files, each node must be started manually.

\textbf{Required files:}

  \item \texttt{launch/spi\_bridge.launch.py} -- lifecycle node management
  \item \texttt{launch/safety\_monitor.launch.py} -- safety system
  \item \texttt{launch/sensors.launch.py} -- LiDAR + IMU (when available)
  \item \texttt{config/hardware\_params.yaml} -- motor model, wheel geometry
  \item \texttt{config/ekf\_config.yaml} -- EKF sensor fusion
  \item \texttt{rviz/star\_default.rviz} -- default visualization
\end{itemize}

\section{UI Gaps (star-ui, TypeScript/React)}

\subsection{Motor Dynamics Model}

From MATLAB system identification (\texttt{matlab/motor\_model\_1st\_order.m}):

\[G(s) = \frac{K}{\tau s + 1} = \frac{3.665}{0.075s + 1}\]

Discrete-time (backward Euler, $T = 0.01$\,s at 100\,Hz):
\[v[k] = (1 - e^{-T/\tau}) \cdot K \cdot u[k] + e^{-T/\tau} \cdot v[k-1]\]
\[\approx 0.1248 \cdot 3.665 \cdot u[k] + 0.8752 \cdot v[k-1]\]

\begin{lstlisting}[language={[GNU]C++}, caption={Motor simulation Go implementation}]
// star-gateway/cmd/virtual_rx72n/motor_sim.go
type MotorSim struct {
    velocityRadps float64    // Current angular velocity (rad/s)
    positionRad   float64    // Accumulated angle (rad)
    encoderTicks  atomic.Int64
    mu            sync.Mutex
}

func (m *MotorSim) Update(pwmDuty float64) {
    m.mu.Lock()
    defer m.mu.Unlock()

    // Clamp duty cycle to [-1.0, 1.0]
    pwmDuty = math.Max(-1.0, math.Min(1.0, pwmDuty))

    // First-order discrete-time system (backward Euler)
    const K   = 3.665   // DC gain: rad/s per volt
    const tau = 0.075   // Time constant: seconds
    const T   = 0.010   // Sample period: 100 Hz
    const Vs  = 12.0    // Supply voltage

    alpha := math.Exp(-T / tau)
    inputVoltage := pwmDuty * Vs
    m.velocityRadps = (1-alpha)*K*inputVoltage + alpha*m.velocityRadps

    m.positionRad += m.velocityRadps * T
    const ticksPerRev = 1364  // 341 PPR * 4 (quadrature)
    m.encoderTicks.Store(int64(m.positionRad / (2 * math.Pi) * ticksPerRev))
}
\end{lstlisting}
